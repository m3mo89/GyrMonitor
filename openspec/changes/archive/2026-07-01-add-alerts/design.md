## Context

`add-alerts` implements the alert phase from `knowledge-base/10-roadmap/phase-6-alerts.md`. The source-of-truth behavior lives in `knowledge-base/02-domain/alerts.md`, `knowledge-base/02-domain/risk-analysis.md`, `knowledge-base/05-api/alerts.md`, and the backend architecture/testing guidance under `knowledge-base/06-engineering/`.

The current backend already has cattle, authentication, activity events, observations, runtime, database persistence, and backend test-suite specs. Activity events expose the boundary needed for later risk and alert generation, including traceability to cattle, event ids, capture time, inactivity duration, and source. This change adds the missing alert module and integrates it into event registration without broadening the MVP into notifications, assignment, dashboard aggregation, offline alert sync, or observation creation.

## Goals / Non-Goals

**Goals:**

- Implement the Alerts module using the established Clean Architecture layout documented in `knowledge-base/06-engineering/backend/clean-architecture-layout.md`.
- Generate alerts from eligible inactivity events when backend risk-threshold evaluation determines attention is required.
- Persist alerts in MariaDB with relationships to cattle and source activity events, consistent with `knowledge-base/06-engineering/database/migrations.md`.
- Expose the Alerts API documented in `knowledge-base/05-api/alerts.md`.
- Enforce the alert lifecycle documented in `knowledge-base/02-domain/alerts.md`.
- Add automated tests around alert generation, authorization, filtering, detail lookup, status transitions, persistence, and event traceability.

**Non-Goals:**

- Notification delivery, escalation, alert assignment, SLA tracking, or deduplication windows.
- Dashboard risk rankings or alert aggregate metrics beyond preserving data needed by future dashboard work.
- Mobile/offline alert synchronization.
- Observation creation from alert detail; observations stay covered by the existing observations capability.
- Veterinary diagnosis or machine-learning risk scoring. MVP risk behavior remains deterministic and transparent per `knowledge-base/02-domain/risk-analysis.md`.

## Decisions

1. Create an `alerts` backend module with domain, application, infrastructure, and presentation layers.

   Rationale: Alerts are listed as a business module in `knowledge-base/06-engineering/backend/modules.md`, and keeping alert lifecycle rules in a dedicated module prevents event registration from owning alert consultation or status changes.

   Alternative considered: add alert logic directly inside `activity-events`. That would make event registration too broad and would blur ownership of status transitions, filtering, and detail lookup.

2. Model risk evaluation as an application/domain dependency invoked from event registration for accepted inactivity events.

   Rationale: `knowledge-base/02-domain/risk-analysis.md` says the backend is authoritative for risk calculation and that sufficiently high risk must trigger alert evaluation. The activity-events capability already defines the integration boundary, so event registration can call a risk evaluator and alert creator without exposing database or HTTP details to the use case.

   Alternative considered: expose a separate manual alert generation endpoint. The KB states alerts are generated by backend rules rather than frontend clients, so this is not part of the MVP API.

3. Persist alerts with explicit cattle and source-event references.

   Rationale: `knowledge-base/02-domain/alerts.md` requires alerts to reference cattle and, for inactivity, the origin event when available. The database-persistence spec already expects alert relationships and indexes, so the migration should include foreign keys and indexes for common alert filters.

   Alternative considered: store denormalized alert snapshots only. That would simplify reads but weaken traceability to source activity events and future observations.

4. Keep the MVP severity/threshold policy deterministic and configuration-friendly.

   Rationale: The risk-analysis KB recommends a simple transparent rule-based MVP. The implementation can use fixed or environment-backed thresholds as long as behavior is deterministic and tested; later validation can tune thresholds without changing API contracts.

   Alternative considered: data-driven or ML-based scoring. That is explicitly a future improvement in the KB and would add avoidable validation risk.

5. Enforce status transitions in the Alerts application layer and persist attended timestamps.

   Rationale: The Alerts domain defines `PENDING`, `IN_PROGRESS`, and `ATTENDED`, with `attendedAt` required for attended alerts. Controllers should delegate validation to use cases/domain services so API and repository behavior stay consistent.

   Alternative considered: allow direct repository patching from the controller. That would duplicate lifecycle rules and make unit testing weaker.

## Risks / Trade-offs

- Risk threshold values are not numerically fixed in the KB -> Mitigation: implement a deterministic MVP policy with tests and keep constants/configuration centralized so later validation can adjust them.
- Event registration now has a side effect beyond storing events -> Mitigation: keep alert generation behind application ports and test idempotent retry behavior so duplicate event submissions do not create duplicate alerts.
- Alert filtering can become slow as records grow -> Mitigation: add MariaDB indexes for status, severity, cattle id, created time, and source event relationship.
- Status updates may race in concurrent clients -> Mitigation: enforce transition rules in the use case and rely on repository persistence checks; add tests for invalid repeated or terminal transitions.
- Future observations/dashboard/offline sync may need more alert fields -> Mitigation: preserve stable identifiers and traceability now, while avoiding speculative API fields not present in `knowledge-base/05-api/alerts.md`.

## Migration Plan

- Add a deterministic MariaDB migration for the alerts table and indexes.
- Wire the alerts module into the backend composition root after repository and use-case tests are in place.
- Integrate alert generation into event registration after the alert repository and risk evaluator are available.
- Keep rollback simple by removing the alerts module and migration before production data exists; destructive rollback after real data requires explicit review per `knowledge-base/06-engineering/database/migrations.md`.

## Open Questions

- Exact numeric score thresholds are not fixed by the KB; implementation should choose a documented MVP default and make it easy to revise during validation.
- The KB requires traceability to users for attended alerts, but `knowledge-base/05-api/alerts.md` only shows `status` and `attendedAt` in the PATCH request. Implementation should preserve actor identity from the authenticated request if existing patterns support it, without expanding the public DTO unless specs are updated.
