## Context

`desktop/GyrMonitor.Desktop` is a `.NET MAUI` app targeting `maccatalyst` and `windows`. Its `Resources/Styles/Colors.xaml` and `Styles.xaml` are still the stock files generated by the MAUI project template: an unused purple accent palette, a `Headline`/`SubHeadline` style pair that most pages never reference, and no card/badge/empty-state styles. Feature pages (`LoginPage`, `DashboardPage`, `CattlePage`, `AlertsPage`, `SyncPage`, `EventSimulatorPage`) build their UI directly from bare `Label`, `Entry`, `Button`, and `Grid`/`CollectionView` elements with ad hoc `Padding`/`Spacing` values and literal color names (`Red`, `Gray`, `Crimson`). There is no existing design token system, icon set, or component library to build on, and no designer on the project — this is a solo engineering pass to bring the app to a visually coherent baseline.

## Goals / Non-Goals

**Goals:**
- Establish one shared visual language (palette, spacing scale, typography, reusable styles) in `Resources/Styles/` that every desktop page draws from.
- Bring each existing screen up to that visual language without changing its behavior, bindings, or navigation.
- Support both light and dark OS themes, since MAUI desktop targets (Windows, macOS) both respect system theme.
- Keep changes confined to XAML/resource-dictionary styling and the minimal code-behind/converters needed for it (e.g., a severity-to-brush converter). No ViewModel or backend changes.

**Non-Goals:**
- No new features, screens, or navigation changes.
- No animation/motion system — static visual polish only.
- No custom control templates requiring platform-specific renderers beyond standard MAUI styling.
- No accessibility audit beyond not regressing default MAUI control accessibility (full a11y pass is out of scope).

## Decisions

**1. Token-based resource dictionaries, not a UI component library.**
Add design tokens (colors, spacing, corner radius, font sizes) as keyed resources in `Colors.xaml` and a new `Spacing.xaml`, plus implicit and explicit `Style` entries in `Styles.xaml` (e.g. `CardStyle`, `SectionHeaderStyle`, `PrimaryButtonStyle`, `BadgeStyle`). Alternative considered: pull in a third-party MAUI UI kit (e.g. Syncfusion, Telerik). Rejected — adds a licensing/dependency burden for what is a styling problem solvable with MAUI's built-in `ResourceDictionary`/`Style` system.

**2. Semantic color aliases layered over raw brand colors.**
Keep raw palette values (`Primary`, `Gray100`...`Gray950`) as today, but add semantic aliases (`SurfaceBrush`, `SurfaceCardBrush`, `TextPrimaryBrush`, `TextSecondaryBrush`, `ErrorBrush`, `SeverityHighBrush`, `SeverityMediumBrush`, `SeverityLowBrush`, `StatusPendingBrush`, `StatusSyncedBrush`) each with an `AppThemeBinding` for Light/Dark. Pages bind to semantic aliases, never raw literals like `Red`/`Crimson`/`Gray`. This is what lets a single palette change propagate everywhere and keeps dark mode correct.

**3. Card/list-row styling via implicit `Style` + `Border`, not custom renderers.**
Use MAUI's `Border` control (with `StrokeShape="RoundRedRectangle"`/`RoundRectangle`) styled via `CardStyle` for metric tiles and list rows, applied directly in each page's `CollectionView.ItemTemplate`/`Grid`. This is the standard MAUI-recommended way to get card visuals without custom drawing.

**4. Tab icons as font-icon glyphs (e.g. a small SVG-per-icon set) added to `Resources/Images`, referenced from `AppShell.xaml`'s `ShellContent.Icon`.**
Alternative considered: embed a full icon font (e.g. FontAwesome via NuGet). Rejected for this pass — only 5 tab icons are needed (Dashboard, Cattle, Alerts, Simulator, Sync); adding 5 small SVGs avoids a new dependency and keeps bundle size predictable. If more icons are needed later, an icon font can be introduced in a follow-up change.

**5. Empty-state as a small reusable `EmptyStateView` shared control (code file + XAML), not per-page duplication.**
`CattlePage`, `AlertsPage`, `DashboardPage` (risk ranking), and `SyncPage` all need "no data yet" messaging. A single `Shared/Controls/EmptyStateView.xaml` (icon/glyph + title + optional subtitle) bound to each page's existing `IsBusy`/collection-empty condition avoids four near-identical copies.

## Risks / Trade-offs

- [Risk] Styling changes to shared `Styles.xaml`/`Colors.xaml` could visually break a page not explicitly covered by this change (e.g. `EventSimulatorPage` beyond the noted grid). → Mitigation: keep raw color keys backward-compatible (don't rename/remove existing keys, only add semantic aliases and new styles), and pass over every page under `Features/` in the task list before considering the change done.
- [Risk] `Border`-based card styling can render slightly differently between macCatalyst and Windows (corner radius, shadow support). → Mitigation: verify visually on both configured targets before closing out; keep shadow effects subtle/optional so their absence on a platform isn't jarring.
- [Risk] Introducing `AppThemeBinding`-based semantic brushes could reveal current hard-coded assumptions (e.g. white backgrounds) that look wrong in dark mode once toggled. → Mitigation: manually toggle OS theme during verification for each restyled page.
- [Trade-off] Building a small custom `EmptyStateView` instead of inlining markup per page adds one new shared control, slightly increasing scope, in exchange for avoiding four divergent copies of the same layout.

## Migration Plan

Purely additive/visual — no data migration. Rollout is a normal code change:
1. Land palette/spacing/style resource changes first (non-breaking, additive keys).
2. Migrate one page at a time (Login → Dashboard → Alerts → Cattle → Sync → EventSimulator) to the new styles, verifying each in the running app before moving to the next.
3. Add tab icons last, once icon assets are in place.
Rollback is a plain revert of the affected XAML/resource files; no runtime state is affected.
